# Как строить LL(1)-таблицу руками и зачем нужен генератор

## Главная идея

В 2.3 таблица разбора строилась вручную. Это учебный этап: нужно понять, как
работает предсказывающий анализатор.

В 3.1 таблица строится автоматически. Мы больше не сопровождаем таблицу руками,
а сопровождаем грамматику:

```text
меняем грамматику
        |
        v
запускаем генератор
        |
        v
получаем новую таблицу
```

Совпадение ручной и сгенерированной таблиц — это не проблема, а доказательство:
генератор правильно воспроизвёл таблицу из 2.3.

## Что такое таблица предсказывающего разбора

Таблица отвечает на вопрос:

```text
если на вершине стека нетерминал A
и текущий входной токен равен t,
какое правило A -> ... нужно применить?
```

Ключ таблицы:

```text
(нетерминал, lookahead)
```

Значение таблицы:

```text
правая часть правила
```

Пример:

```python
("Rule", TokenType.AXIOM): ["AxiomRule"]
("Rule", TokenType.NONTERM): ["NtermRule"]
```

Это означает:

```text
если разбираем Rule и видим `axiom, применяем Rule -> AxiomRule
если разбираем Rule и видим обычный нетерминал, применяем Rule -> NtermRule
```

## Как строить таблицу руками

Для каждой продукции:

```text
A -> alpha
```

нужно сделать следующее.

### 1. Найти FIRST(alpha)

`FIRST(alpha)` — это множество терминалов, с которых может начинаться цепочка
`alpha`.

Если `alpha` может быть пустой, в `FIRST(alpha)` добавляется `epsilon`.

Пример:

```text
Rule -> NtermRule | AxiomRule
NtermRule начинается с NONTERM
AxiomRule начинается с AXIOM
```

Значит:

```text
FIRST(NtermRule) = { NONTERM }
FIRST(AxiomRule) = { AXIOM }
```

И в таблице появляются ячейки:

```python
("Rule", TokenType.NONTERM): ["NtermRule"]
("Rule", TokenType.AXIOM): ["AxiomRule"]
```

### 2. Заполнить таблицу по FIRST

Для каждого терминала `t` из `FIRST(alpha)`, кроме `epsilon`, записываем:

```text
table[A, t] = alpha
```

Пример:

```text
Start -> Grammar EOF
FIRST(Grammar EOF) = { AXIOM, NONTERM }
```

Значит:

```python
("Start", TokenType.AXIOM): ["Grammar", TokenType.EOF]
("Start", TokenType.NONTERM): ["Grammar", TokenType.EOF]
```

### 3. Если возможен epsilon, использовать FOLLOW

Если:

```text
epsilon ∈ FIRST(alpha)
```

то нужно взять `FOLLOW(A)` и для каждого терминала `t` из `FOLLOW(A)` записать:

```text
table[A, t] = epsilon
```

Пример:

```text
GrammarTail -> Rule GrammarTail | epsilon
```

`GrammarTail` может быть пустым. Если после `GrammarTail` может идти `EOF`, то:

```python
("GrammarTail", TokenType.EOF): [EPSILON_SYMBOL]
```

### 4. Проверить конфликты

Если две разные продукции хотят попасть в одну и ту же ячейку таблицы, значит
грамматика не LL(1).

Пример плохой грамматики:

```text
S -> "a" | "a" "b"
```

Обе альтернативы начинаются с `"a"`, поэтому обе хотят занять ячейку:

```text
(S, "a")
```

Это LL(1)-конфликт.

## Что нужно помнить при ручном построении

При ручном заполнении таблицы нужно не забыть:

- посчитать `FIRST` для каждой правой части правила;
- посчитать `FOLLOW` для нетерминалов, у которых есть `epsilon`;
- для обычных правил заполнить таблицу по `FIRST`;
- для `epsilon`-правил заполнить таблицу по `FOLLOW`;
- добавить `EOF` в `FOLLOW` аксиомы;
- не перепутать терминалы и нетерминалы;
- проверить, что нет двух разных правил в одной ячейке;
- проверить, что все нужные lookahead-токены покрыты;
- проверить, что все используемые нетерминалы имеют правила.

Именно поэтому ручная таблица неудобна для сопровождения.

## Где у нас ручная таблица

Ручная таблица из 2.3 находится в:

```text
src/grammar_parser.py
```

Функция:

```python
build_manual_table()
```

Она нужна для первого запуска генератора:

```text
ручная таблица
        |
        v
разобрать generator_grammar.txt
        |
        v
сгенерировать generated/generated_input_table.py
```

## Где у нас автоматическая генерация

Автоматическая генерация таблицы происходит в:

```text
src/table_builder.py
```

Главные функции:

```python
build_first()
build_follow()
build_parse_table()
put_table_cell()
```

Запись таблицы в Python-файл происходит в:

```text
src/table_emitter.py
```

Главная функция:

```python
emit_python_table()
```

Вся цепочка связана в:

```text
src/generator.py
```

Функция:

```python
generate_table()
```

## Зачем нужна сгенерированная таблица, если она такая же

Она должна быть такой же.

Ручная таблица:

```text
правильная, но написанная руками
```

Сгенерированная таблица:

```text
правильная и построенная автоматически по грамматике
```

Если они совпали, значит генератор правильно строит таблицу.

## Почему ручная таблица всё равно осталась в коде

Для первого запуска возникает bootstrap-проблема:

```text
чтобы сгенерировать таблицу, нужно разобрать грамматику
чтобы разобрать грамматику, нужна таблица
```

Поэтому первый запуск использует ручную таблицу из 2.3.

После первого запуска можно использовать сгенерированную таблицу:

```bash
python3 generator.py generator_grammar.txt generated/generated_input_table_2.py \
  --mode enum --bootstrap-table generated/generated_input_table.py
```

Это означает:

```text
читать generator_grammar.txt уже сгенерированной таблицей
```

## Как объяснить на защите

Короткая формулировка:

> В 2.3 таблица была написана вручную. В 3.1 я использую анализатор из 2.3,
> чтобы прочитать описание грамматики, затем автоматически строю FIRST, FOLLOW
> и новую таблицу. Совпадение ручной и сгенерированной таблицы показывает, что
> генератор правильно воспроизвёл стартовую таблицу. После этого ручная таблица
> нужна только как bootstrap для первого запуска.

Ещё короче:

> Мы больше не правим таблицу руками. Мы правим грамматику, а таблицу строит
> генератор.
