# Ориентир для сдачи лабораторной работы

## 1. Что нужно уметь объяснить

Цель работы — показать использование `flex` и `bison` для реализации
сильного форматтера учебного диалекта Бейсика.

Главная мысль:

> Lexer превращает символы в токены, parser проверяет грамматику и
> запускает семантические действия, а семантические действия выводят
> исходную программу в едином стиле.

Не следует представлять программу как набор замен строк. Форматирование
основано на синтаксической структуре. Поэтому отступ увеличивается
именно внутри блоков, а пробелы в выражениях расставляются после разбора
операций с учётом их приоритета.

## 2. Подготовка перед сдачей

Из корня лабораторной выполнить:

```sh
make clean
make
make test
make test2
```

Ожидаемый результат:

```text
All tests passed
```

Для ручной демонстрации:

```sh
./basic-formatter tests/example.bas
```

Для демонстрации ошибки:

```sh
make test2
```

Formatter должен сообщить позицию ошибки. Скрипт `tests/run-invalid.sh`
считает такой запуск успешным, если formatter завершился с ошибкой.

## 3. План демонстрации

### Шаг 1. Сформулировать задачу

Сказать:

> Реализован сильный форматтер диалекта Бейсика. Он удаляет
> комментарии, обрабатывает переносы через `_`, нормализует пробелы и
> расставляет строки и отступы по структуре программы. При первой
> синтаксической ошибке работа прекращается.

Почему это важно: преподаватель сразу видит соответствие условию и
понимает границы реализации. Ачивки намеренно не реализованы.

### Шаг 2. Показать вход и выход

Открыть `tests/example.bas`, затем выполнить:

```sh
./basic-formatter tests/example.bas
```

Обратить внимание на:

- удаление комментариев;
- пробелы вокруг операций;
- пробел после запятой;
- отступы внутри функций, условий и циклов;
- склейку строки после `_`;
- единый синтаксис обращений через круглые скобки.

Почему так: это наблюдаемый результат работы форматтера, а не только
внутренняя реализация.

### Шаг 3. Показать lexer

Открыть `src/lexer.l`.

Показать:

- `%option reentrant`;
- `%option caseless`;
- правило комментария;
- правило переноса `_`;
- `NEWLINE`;
- правила `IDENT` и `SUB_IDENT`;
- `YY_USER_ACTION`.

Объяснить:

> Переводы строк значимы, поэтому обычный конец строки становится
> токеном `NEWLINE`. Конец строки после `_` игнорируется. Комментарий
> удаляется lexer. `caseless` нужен для регистронезависимых ключевых
> слов. `SUB_IDENT` отделён от `IDENT`, потому что имя процедуры не
> обязано иметь суффикс типа.

### Шаг 4. Показать parser

Открыть `src/parser.y`.

Показать:

- `%define api.pure full`;
- `%lex-param` и `%parse-param`;
- правила `function`, `sub`, `statement`;
- правила `if_stmt`, `for_stmt`, `do_stmt`;
- приоритеты операций;
- правило `variable`;
- `%destructor`.

Объяснить:

> Parser реентрантный: scanner и formatter передаются параметрами,
> изменяемых глобальных переменных нет. Правила грамматики отражают
> конструкции языка. Семантические действия собирают выражения и
> передают готовые строки модулю форматирования.

### Шаг 5. Показать управление отступами

Открыть `src/formatter.c`.

Объяснить:

> В `struct Formatter` хранится текущий уровень отступа. При входе в
> блок он увеличивается, при выходе уменьшается. Для `Else` сначала
> уменьшается отступ, затем печатается `Else`, затем отступ
> восстанавливается для тела ветви.

### Шаг 6. Показать ошибку

Выполнить:

```sh
./basic-formatter tests/invalid.bas
```

Объяснить:

> Parser прекращает работу при первой синтаксической ошибке. Координаты
> вычисляются lexer и передаются через механизм locations Bison.

В тестах ожидаемый вывод ошибки вынесен отдельно:
`make test2` запускает `tests/run-invalid.sh`. Для него нет `diff` и
нет expected-файлов: цель теста — показать, что некорректный вход
действительно приводит к синтаксической ошибке.

### Шаг 7. Показать тесты

Открыть `tests/run.sh` и выполнить:

```sh
make test
```

Объяснить:

> Позитивные тесты сравниваются с ожидаемым выводом через `diff`.
> Фактический вывод остаётся в `.actual`, чтобы его можно было открыть.
> Формы `Do Loop` вынесены в отдельный позитивный тест, чтобы проверить
> каждую форму из условия.

После этого выполнить:

```sh
make test2
```

Объяснить:

> Это отдельный ошибочный тест. Он не сравнивается с expected-файлом, а
> просто демонстрирует сообщение parser и проверяет, что formatter
> завершился с ошибкой.

## 4. Карта файлов

| Файл                 | Что показывать                                     |
| -------------------- | -------------------------------------------------- |
| `src/lexer.l`        | Токены, комментарии, `_`, `NEWLINE`, позиции       |
| `src/parser.y`       | Реентрантность, грамматика, семантические действия |
| `src/formatter.c`    | Механизм отступов и печати строк                   |
| `src/main.c`         | Создание scanner и запуск `yyparse`                |
| `Makefile`           | Генерация Flex/Bison и компиляция                  |
| `tests/example.bas`  | Основной пример                                    |
| `tests/do-loops.bas` | Все дополнительные формы `Do Loop`                 |
| `tests/invalid.bas`  | Вход для отдельного ошибочного теста `make test2`  |
| `tests/run-invalid.sh` | Запуск ошибочного теста без `diff`               |

## 5. Возможные вопросы и ответы

### Что такое сильный форматтер?

Сильный форматтер может вставлять переводы строк, а не только пробелы.
Также по условию он должен удалять комментарии. В этой реализации
комментарии удаляются lexer, а расположение строк определяется parser.

### Чем сильный форматтер отличается от слабого?

Слабый форматтер не может вставлять переводы строк и должен сохранять
комментарии. Слабый форматтер относится к дополнительным ачивкам и здесь
не реализован.

### Зачем использовать Bison, если можно заменить пробелы регулярными выражениями?

Регулярных выражений недостаточно для вложенных блоков и приоритетов
операций. Parser знает структуру программы: где начинается и
заканчивается блок, какая операция вложена в какую, где находится
ветвь `Else`. Поэтому форматирование корректно работает при
произвольной вложенности.

### Что делает Flex?

Flex генерирует lexer из файла `src/lexer.l`. Lexer читает символы и
возвращает parser токены: ключевые слова, идентификаторы, числа,
строки, операции и значимые переводы строк.

### Что делает Bison?

Bison генерирует parser из файла `src/parser.y`. Parser проверяет,
соответствует ли последовательность токенов грамматике, и выполняет
семантические действия для формирования вывода.

### Почему анализаторы называются реентрантными?

Их изменяемое состояние не хранится в глобальных переменных. Scanner
создаётся как отдельный объект `yyscan_t`, а scanner и formatter явно
передаются в `yyparse`. Можно независимо создать несколько экземпляров
анализатора.

### Почему перевод строки является токеном?

В данном диалекте Бейсика переводы строк значимы и разделяют операторы.
Если игнорировать их как обычные пробелы, parser не сможет надёжно
определить границы операторов.

### Как работает перенос строки через `_`?

Lexer распознаёт `_`, возможные пробелы, необязательный комментарий и
следующий перевод строки как одну конструкцию и полностью её
отбрасывает. Для parser это продолжение текущей строки.

### Почему комментарии удаляются в lexer?

Для сильного форматтера комментарии не влияют на синтаксическую
структуру и должны быть удалены. Lexer уже видит текст посимвольно,
поэтому удаление комментария до конца строки проще и естественнее
сделать именно там.

### Зачем нужны `IDENT` и `SUB_IDENT`?

Переменные и функции имеют суффикс типа: `%`, `&`, `!`, `#` или `$`.
Имя процедуры `Sub` в примере суффикса не имеет. Поэтому lexer
возвращает разные токены и parser явно ограничивает допустимые места их
использования.

### Почему вызов функции и индексирование массива объединены?

В условии сказано, что обе конструкции записываются через круглые
скобки и синтаксически неразличимы. Поэтому правило `variable`
представляет обе конструкции одинаково.

### Почему не поддерживаются квадратные скобки?

В актуальном условии сказано, что вызов функции и индексирование массива
записываются через круглые скобки. Поэтому символы `[` и `]` не входят в
допустимые разделители лексера.

### Как задаются приоритеты операций?

Директивами `%left` и `%precedence` в `src/parser.y`. Сравнения имеют
меньший приоритет, затем идут `+` и `-`, затем `*` и `/`, затем
унарный минус.

### Почему для `Do Loop` есть отдельные `do_body` и `do_tail`?

У нескольких форм общий префикс `Do` и общий фрагмент тела. Выделение
общих частей делает грамматику однозначной и позволяет поддержать
постусловия `Loop While` и `Loop Until` без конфликтов Bison.

### Как рассчитываются координаты ошибки?

Макрос `YY_USER_ACTION` в `src/lexer.l` обновляет текущую строку и
столбец после каждого совпадения. Flex передаёт диапазон токена в
`YYLTYPE`, а `yyerror` печатает начальную позицию ошибочного токена.

### Почему часть вывода может появиться до сообщения об ошибке?

Форматтер работает потоково: семантические действия печатают уже
распознанные конструкции. После первой ошибки дальнейший разбор
останавливается, но корректный префикс уже мог быть выведен.

### Как проверяется корректность?

`make test` запускает `tests/run.sh`. Позитивные примеры сравниваются с
ожидаемыми файлами через `diff`, а `.actual` остаются для просмотра.
Ошибочный пример запускается отдельно через `make test2` и должен
завершиться с ошибкой.

### Что не реализовано?

Не реализованы дополнительные ачивки: слабый formatter и ограничение
длины строк. Основная обязательная часть лабораторной реализована.

## 6. Краткий чек-лист

- Выполнить `make clean && make && make test && make test2`.
- Показать форматирование `tests/example.bas`.
- Показать остановку на `tests/invalid.bas`.
- Объяснить цепочку Flex → Bison → семантические действия → formatter.
- Показать реентрантность в `src/lexer.l` и `src/parser.y`.
- Показать значимые `NEWLINE`, комментарии и перенос `_`.
- Показать управление отступами в `src/formatter.c`.
- Быть готовым объяснить приоритеты выражений и пять форм `Do Loop`.
