# Лабораторная работа 3.3: как устроено решение

## 1. Зачем нужна эта лабораторная

Лексический анализ отвечает на вопрос: «из каких токенов состоит текст?».
Синтаксический анализ проверяет, можно ли собрать токены по правилам
грамматики, и строит абстрактное синтаксическое дерево (AST).

Однако синтаксически правильная программа ещё не обязательно имеет
смысл. Например:

```pascal
type
  Vector = array 1..Count of INTEGER;
const
  Count = 10;
```

Грамматика допускает такой текст, но по условию лабораторной имя
`Count` нельзя использовать до объявления. Эту ошибку обнаруживает
третья фаза компиляции — семантический анализ.

В лабораторной 2.2 файл `main.py` завершал работу после построения AST.
В лабораторной 3.3 дерево становится исполняемой моделью деклараций:
узлы обходятся сверху вниз, проверяют ограничения языка и вычисляют
атрибуты — значения констант и размеры типов.

## 2. Что требуется проверить

Индивидуальный вариант задаёт три обязательных ограничения:

1. Используемые идентификаторы определены выше по тексту.
2. Имена типов и констант находятся в общем пространстве имён и не
   повторяются. Элементы перечислений тоже объявляют константы.
3. В одной записи `record` отсутствуют одноимённые поля.

Дополнительно программа должна:

- вывести значения всех констант;
- пронумеровать элементы перечислений с нуля;
- вычислить размер каждого объявленного типа;
- при ошибке вывести её координату и описание.

## 3. Общий поток обработки

Запуск начинается в функции `analyze_file()` из `main.py`:

```python
tree = build_parser().parse(source.read())
tree.check()
print(tree.format_result())
```

Здесь явно видны две разные фазы:

1. `parse()` проверяет конкретный синтаксис и строит AST.
2. `check()` выполняет семантический обход уже построенного дерева.

Разделение полезно и теоретически, и практически. Грамматика занимается
формой программы, а методы AST — её контекстными ограничениями.

## 4. Координаты и `ExAction`

Обычное семантическое действие `parser_edsl` получает только атрибуты
символов правила. Для понятной ошибки этого недостаточно: анализатор
должен знать, где в исходном тексте встретилось проблемное имя.

Расширенное действие `pe.ExAction` получает:

- `attrs` — атрибуты символов правила;
- `coords` — координаты символов правила;
- `res_coord` — координату результата.

Например, узел ссылки на именованный тип сохраняет позицию
идентификатора:

```python
@staticmethod
@pe.ExAction
def create(attrs, coords, res_coord):
    name, = attrs
    return NamedType(name, coords[0].start)
```

Если тип не найден, ошибка относится именно к этому месту:

```text
Ошибка (2, 12): Имя MISSING не определено выше по тексту
```

Координаты сохраняются только в потенциально ошибочных узлах. Это
служебная информация AST: она не описывает смысл конструкции, но нужна
для качественной диагностики.

## 5. Таблица символов

Символ в терминах лекции — именованная сущность программы вместе с её
описанием. В решении используются два вида глобальных символов:

```python
ConstSymbol(name, value)
TypeSymbol(name, type_info)
```

`SymbolTable` хранит отображение имени в символ. Метод `add()` отвергает
повторное имя, а `find()` — обращение к ещё не объявленному имени.

Глобальная таблица создаётся в `SemanticContext`. Типы, обычные
константы и элементы перечислений добавляются в одну таблицу. Поэтому
такой текст корректно считается ошибочным:

```pascal
const Answer = 42;
type Answer = INTEGER;
```

Каждый `RecordType` создаёт отдельную локальную таблицу полей. Это
упрощённое применение идеи локальных таблиц из лекции № 6: имена полей
проверяются внутри записи и не смешиваются с глобальными именами.

Полный вариант на дополнительный балл потребовал бы хранить ссылки на
таблицы открытых областей и выполнять рекурсивный поиск по ним. Для
обязательной части этой работы он не нужен: язык не содержит выражений
доступа к полям и сложных правил экранирования.

## 6. Почему важен порядок обхода

`Program.check()` обходит секции и декларации в исходном порядке.
Сначала вычисляется правая часть объявления, затем новое имя попадает
в таблицу:

```python
info = self.type_expr.evaluate(ctx)
ctx.add_type(self.name.name, info, self.name.pos)
```

Благодаря этому ссылка на ранее объявленный тип разрешается, а ссылка
вперёд завершается ошибкой.

Есть одно осознанное исключение: указатель может ссылаться на
определяемый сейчас тип. Оно нужно для структур наподобие списка:

```pascal
type
  List = record
    next: ^List
  end;
```

Размер указателя известен независимо от размера объекта, поэтому
рекурсивное определение остаётся вычислимым.

## 7. Вычисление констант

Узлы `IntConst`, `RealConst`, `IdentConst` и `UnaryConst` реализуют
метод `evaluate()`.

Примеры:

```pascal
const
  Width = 640;
  Neg = -5;
type
  Row = array 1..Width of CHAR;
```

`IdentConst` ищет имя в глобальной таблице и убеждается, что найден
именно `ConstSymbol`, а не тип. Перечисление добавляет константы в
глобальную таблицу последовательно:

```pascal
type Color = (red, green, blue);
```

даёт:

```text
RED = 0
GREEN = 1
BLUE = 2
```

## 8. Вычисление размеров типов

Для каждого типа вычисляется объект:

```python
TypeInfo(size, cardinality=None)
```

`size` — размер значения в байтах. `cardinality` — количество возможных
значений конечного порядкового типа. Второй атрибут нужен для массивов
и множеств.

Приняты следующие размеры:

| Тип | Размер |
| --- | ---: |
| `INTEGER` | 2 байта |
| `REAL` | 4 байта |
| `CHAR` | 1 байт |
| `BOOLEAN` | 1 байт |
| перечисление | 2 байта |
| диапазон | 2 байта |
| указатель | 4 байта |

Условие явно задаёт размеры `INTEGER`, `REAL`, перечислений и
указателей. Размеры `CHAR` и `BOOLEAN` в условии не оговорены, поэтому
для них в реализации приняты стандартные учебные значения.

Составные типы вычисляются рекурсивно:

- массив: `число индексов * размер элемента`;
- множество: `ceil(число возможных элементов / 8)`;
- обычная запись: сумма размеров полей;
- `case`-часть записи: размер поля тега плюс размер наибольшей ветви.

Для примера:

```pascal
type
  Color = (red, green, blue);
  Palette = set of Color;
```

тип `Palette` занимает `ceil(3 / 8) = 1` байт.

## 9. Вариантные записи

Для записи:

```pascal
type
  Kind = (small, large);
  Item = record
    fixed: INTEGER;
    case tag: Kind of
      small: (letter: CHAR);
      large: (number: REAL)
  end;
```

размер равен:

```text
fixed + tag + max(letter, number) = 2 + 2 + max(1, 4) = 8 байт
```

Метки ветвей `small` и `large` вычисляются как обычные константные
выражения. Поэтому неопределённая метка также будет обнаружена.

## 10. Как запустить и проверить

Из каталога `lab9`:

```sh
python3 main.py assets/input.txt
```

Если аргумент не указан, используется тот же файл по умолчанию:

```sh
python3 main.py
```

Автоматические тесты:

```sh
sh tests/run.sh
```

Тесты проверяют:

- вычисление значений констант и размеров типов;
- размер вариантной записи;
- ссылку на имя до объявления;
- общий namespace типов и констант;
- конфликт элемента перечисления с существующей константой;
- повторное поле записи;
- некорректный диапазон.

## 11. Как разбирать решение на защите

Удобный порядок объяснения:

1. Показать, что синтаксическая корректность не гарантирует
   семантическую корректность.
2. Показать `SemanticContext` и общую таблицу типов и констант.
3. Показать `ExAction` на примере `NamedType.create()`.
4. Объяснить последовательный обход деклараций в `Program.check()`.
5. Разобрать рекурсивное вычисление размеров на примере массива,
   множества и вариантной записи.
6. Запустить корректный пример и один пример с ошибкой.

Главная идея лабораторной: AST — не только удобная форма хранения
программы. После синтаксического анализа оно становится основой для
проверки контекстных правил и накопления информации, необходимой
следующим фазам компилятора.
